# 自我挑战语言模型智能体

## 核心贡献

本文提出了 Self-Challenging Agent (SCA) 框架，通过让智能体自己生成训练任务来解决多轮工具使用场景中训练数据稀缺的问题。核心创新是 Code-as-Task (CaT) 任务表示方法：每个任务包含指令、验证函数、示例解决方案和失败案例四个组件，全部用代码表达以确保任务的可行性、可验证性和难度。智能体扮演两个角色：(1) 任务挑战者（Challenger）通过与环境交互生成高质量任务；(2) 任务执行者（Executor）在这些自生成任务上通过强化学习训练。在 M³ToolEval 和 TauBench 两个基准上，仅使用自生成数据就使 Llama-3.1-8B-Instruct 的成功率提升超过两倍（从 12.0% 到 23.5%），在蒸馏设置下平均提升 20.2%。

## 方法详解

### 双角色框架

**任务挑战者（Task Challenger）**：
- 策略 $\pi^{\text{task}}$ 通过与环境交互收集信息
- 采取一系列动作调用不同工具：$a_{t+1} \sim \pi^{\text{task}}(\cdot | o_{0:t+1}, a_{1:t})$
- 最终输出任务规范和验证函数：$\hat{c}, \hat{R}_{\hat{c}} \sim \pi^{\text{task}}(\cdot|o_{0:T}, a_{0:T-1})$
- 生成合成任务集 $\hat{\mathcal{C}}=\{\hat{c}_i\}_{i=1}^N$

**任务执行者（Task Executor）**：
- 策略 $\pi^{\text{exec}}$ 解决挑战者提出的任务
- 在每个时间步输出动作：$a_{t+1} \sim \pi^\text{exec}(\cdot | o_{0:t+1}, a_{1:t})$
- 完成任务后通过验证函数获得奖励：$R_c(s_T,a_T) \in \{0,1\}$

### Code-as-Task (CaT) 任务表示

CaT 通过四个组件确保任务质量：

1. **指令（Instruction）**：发送给执行者的任务描述
2. **验证函数（Verification Function）**：可执行的 Python 代码，检查最终状态和答案是否满足要求
3. **示例解决方案（Example Solution）**：必须能通过验证函数，确保任务可行
4. **失败案例（Failure Cases）**：三个不应通过验证的案例，防止验证函数过于宽松

**自动过滤机制**：
- 验证函数必须是可运行的 Python 代码（通过率 47.7%）
- 示例解决方案必须通过验证函数（通过率 9.5%）
- 所有失败案例都不能通过验证函数（最终通过率 5.2%）

这种严格的过滤显著减少了假阳性（FP）和假阴性（FN），即使挑战者只有 5% 的成功率，仍能收集到大量高质量任务。

### 训练方法

**自我改进（Self-Improvement）**：
- 使用同一个 LLM 同时作为 $\pi^{\text{exec}}$ 和 $\pi^{\text{task}}$
- 应用 one-step REINFORCE 优化：
$$\mathcal{L} = -\sum_{\hat{c}\in \hat{\mathcal{C}}} \mathbb{E}_{a_{1:T} \sim \pi^{\text{exec}}} \left[ \hat{R}_{\hat{c}}(s_T, a_T) \sum_{t=0}^T  \log \pi^{\text{exec}}(a_t|o_{0:t}, a_{0:t-1}) \right]$$
- 由于 0/1 奖励结构，等价于在成功轨迹上进行监督微调（Rejection Fine-Tuning）

**蒸馏（Distillation）**：
- 使用更强的 LLM 在合成任务上生成演示轨迹
- 对较弱的学生模型应用监督微调：
$$\mathcal{L} = - \sum\nolimits_{\{o_{0:T}, a_{0:T}\} \in \hat{\mathcal{D}}} \left[ \sum_{t=0}^{T} \log \pi^{\text{exec}}(a_t|o_{0:t}, a_{0:t-1}) \right]$$
- 即使失败的轨迹也有助于学习（如对错误的反思）

## 实验结果

### 实验环境

**M³ToolEval**：
- **Calculation**：使用旅行规划、DNA 测序、消息解码、交易计算等工具（每个领域约 6 个工具）
- **Web Browsing**：在购物网站上导航和查询信息

**Tau-Bench**：
- **Retail**：电商客服场景，约 15 个工具（如 exchange_order_items）
- **Airline**：航班预订客服场景，约 15 个工具（如 book_flight）

### 主要结果（Llama-3.1-8B）

| 设置 | Calculation | Web Browsing | Retail | Airline | 平均 |
|---|---|---|---|---|---|
| **零样本基线** | 20.3% | 16.2% | 8.9% | 2.5% | 12.0% |
| **蒸馏 - PAE** | 44.3% | 45.6% | 23.7% | 6.7% | 30.1% |
| **蒸馏 - SCA** | **43.2%** | **50.0%** | **28.9%** | **6.7%** | **32.2%** |
| **自我改进 - PAE** | 27.6% | 14.0% | 9.8% | 0.0% | 12.9% |
| **自我改进 - SCA** | **31.8%** | **44.9%** | **13.0%** | **4.2%** | **23.5%** |

**关键发现**：
1. **蒸馏设置**：SCA 平均提升 20.2%，在部分可观察环境（Web Browsing、Retail）中显著优于 PAE
2. **自我改进设置**：SCA 使成功率翻倍（12.0% → 23.5%），相比 PAE 提升 10.6%
3. **泛化能力**：完全在合成任务上训练，却能在真实测试任务上取得显著提升

### 零样本参考性能

- **GPT-4o**：平均 40.0% Pass@1
- **Llama-3.1-70B**：平均 41.3% Pass@1（最强零样本基线）
- **Llama-3.1-8B**：平均 12.0% Pass@1

SCA 训练后的 8B 模型（23.5%）接近 70B 模型零样本性能的一半。

## 与其他方法的对比

### vs. PAE (Proposer-Agent-Evaluator)

| 维度 | PAE | SCA |
|---|---|---|
| 任务生成方式 | 直接从 API 文档生成 | 主动与环境交互后生成 |
| 任务组件 | 仅指令 | 指令 + 验证函数 + 解决方案 + 失败案例 |
| 评估方式 | 提示同一模型作为评判者 | 可执行的验证函数 |
| 适用环境 | 完全可观察环境 | 完全/部分可观察环境 |
| 自我改进性能 | 12.9% | **23.5%** |

**PAE 的局限性**：
- 在部分可观察环境中只能生成模糊任务（如"浏览网站上的产品"）
- 缺乏精确的验证机制，导致假阳性和假阴性
- 在 Airline 环境的自我改进中性能下降到 0%

**SCA 的优势**：
- 挑战者主动探索环境，生成更精确和多样的任务
- CaT 提供可靠的自动评估，无需人工标注
- 在所有环境中都能稳定改进

## 消融实验

### CaT 组件的重要性

人工标注 50 个轨迹的结果：

| 变体 | FN | FP | TN | TP | 通过率 |
|---|---|---|---|---|---|
| PAE | 高 | 中 | 低 | 低 | - |
| 仅验证函数 | 高 | 中 | 低 | 低 | 47.7% |
| + 示例解决方案 | 低 | 高 | 中 | 中 | 9.5% |
| + 失败案例（完整 CaT） | 中 | **0%** | 高 | 高 | 5.2% |

**关键洞察**：
- 示例解决方案消除不可能的任务（减少 FN）
- 失败案例完全消除过于宽松的验证函数（消除 FP）
- 剩余的 FN 主要是语义模糊（如"帮我退最近的订单"未指定哪个订单）

### RL 算法对比

在 Calculation 环境的 Pass@1 结果：

| 算法 | 类型 | 性能 |
|---|---|---|
| Rejection Fine-Tuning | 离线 | 31.8% |
| DPO | 离线 | ~30% |
| GRPO | 在线 | **43.2%** |
| PPO | 在线 | ~40% |

**发现**：
- 在线 RL 可以进一步提升性能（31.8% → 43.2%）
- 但在线方法需要更复杂的基础设施和更仔细的调参
- GRPO 在训练末期可能突然崩溃到 0%（超参数敏感）

### 任务难度分布

使用 Llama-3.1-8B 作为挑战者：
- 过滤前：任务难度分布较分散
- 过滤后：分布更均匀，集中在中等难度

使用 Llama-3.1-70B 作为挑战者：
- 过滤前后分布保持相似
- CaT 仅精炼任务而非折叠分布

**结论**：CaT 过滤主要移除弱模型的无效生成，保留强模型的任务多样性。

### 数据扩展策略

在 Calculation 环境测试两种扩展方式：

**扩展任务数量 vs. 扩展每任务轨迹数**：
- 200 任务：训练集性能提升，测试集性能下降
- 400 任务：测试集仅边际改进
- 800 任务：测试集稳定提升

**关键洞察**：
- 任务多样性比轨迹数量更重要
- 小任务集会导致过拟合（训练集高、测试集低）
- 需要足够大的任务集才能泛化到分布外测试集

## 局限性

1. **假阴性问题**：即使使用完整 CaT，仍有相当比例的假阴性（主要是语义模糊或信息缺失）

2. **与真实任务的性能差距**：在 oracle 任务上训练的性能仍高于 SCA 任务

3. **环境特定技能**：智能体主要提升环境特定技能，而非通用智能体能力

4. **挑战者能力依赖**：弱模型（8B）作为挑战者的任务通过率仅 5.2%，需要大量采样

5. **计算成本**：需要生成大量候选任务并过滤（800 个有效任务可能需要 15,000+ 次尝试）

6. **验证函数局限**：依赖代码执行器和模式匹配，可能无法捕捉所有语义要求

## 关键洞察

1. **主动探索的重要性**：让挑战者与环境交互收集信息，而非仅从初始观察生成任务，这对部分可观察环境至关重要

2. **代码作为通用接口**：用代码表达任务的所有组件（验证、解决方案、失败案例）提供了通用性和表达力，支持自动过滤

3. **质量胜于数量**：严格的自动过滤（5.2% 通过率）确保训练数据质量，即使挑战者经常失败也能收集足够的高质量任务

4. **合成任务的泛化**：完全在自生成任务上训练却能泛化到真实测试任务，证明了任务合成的可行性

5. **任务多样性的关键作用**：扩展任务数量比增加每任务的轨迹数更有效，强调了大规模自动任务生成的价值

6. **自我改进的可行性**：在没有更强模型的情况下，智能体仍能通过自我挑战实现显著改进（12.0% → 23.5%），为完全自主的智能体训练开辟了道路

7. **与 SPICE 的互补性**：SPICE 使用语料库生成推理问题，SCA 通过工具交互生成任务；两者可能结合——SPICE 用于知识密集型推理，SCA 用于工具使用和多轮交互

8. **自我挑战的范式转变**：从依赖人工标注任务转向智能体自己发现和提出有价值的挑战，这与人类学习中的自我驱动探索高度一致
